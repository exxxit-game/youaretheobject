## 1. W3C WebXR Device API and modules (status as of 8 Oct 2026)

Status list checked on the Immersive Web WG publications page (https://www.w3.org/groups/wg/immersive-web/publications/): no WebXR document is a W3C Recommendation yet.

- **WebXR Device API: Candidate Recommendation Draft, 9 June 2026 (last CR Snapshot 31 Mar 2022)** — W3C Immersive Web WG, "WebXR Device API", CRD 2026-06-09, https://www.w3.org/TR/webxr/ — verified yes (read up to §13, about 300k of 465k characters) — "Users must be in control of when immersive sessions are created." — For us: the core API is stable enough to build on; nothing we use is at risk.
- **Session request only inside a user gesture** — same — verified yes — "within the user activation event" — For us: agrees with vr-checklist ("requestSession only from a real user gesture").
- **visibilityState: `visible` / `visible-blurred` (input not processed, frames may be throttled) / `hidden` (frame callbacks paused)** — same, §XRSession — verified yes — (paraphrase) — For us: agrees with our "pause timed events when visible-blurred/hidden"; input is dead in visible-blurred, so timers must also stop there.
- **local-floor must always be available where local is (emulated if needed); unknown floor height "MUST be estimated" and rounded (about 1 cm) against fingerprinting** — same, §reference spaces — verified yes — "through emulation if necessary" — For us: our `local` fallback is harmless but should almost never fire on a conforming browser.
- **`reset` event fires on recalibration or origin jumps after tracking loss, not on brief pose glitches** — same — verified yes — "A reset event MUST NOT be dispatched if the viewer's pose experiences discontinuities." — For us: supports recentering on `reset` (Meta-button recenter), not on every tracking hiccup.
- **The browser must always give an escape to its trusted UI; content that misreports viewpoint can make users ill** — same, §13.4–13.6 — verified yes — "may become disoriented or physically ill" — For us: never fake head motion; the system menu always wins.
- **WebXR Gamepads Module Level 1: Working Draft, 7 July 2025** — W3C, "WebXR Gamepads Module - Level 1", https://www.w3.org/TR/webxr-gamepads-module-1/ — verified yes (full) — "Buttons reserved by the UA or platform MUST NOT be exposed on the Gamepad." — For us: the Meta/system button is never visible to the page; do not design for it.
- **xr-standard mapping: buttons[0] trigger (required), [1] squeeze, [2] touchpad, [3] thumbstick press; axes[0,1] touchpad X/Y, [2,3] thumbstick X/Y; extra buttons follow by importance; missing slots are placeholders (value 0)** — same §3 — verified yes — "SHOULD appear in order of decreasing importance" — For us: read the stick from axes[2]/[3] and the stick click from buttons[3]; never hard-code A/B/X/Y indices from the spec (it defines none).
- **Hand input sources may carry no gamepad; if the source lacks the minimum controls "the gamepad attribute MUST be null"** — same §2.1 — verified yes — "the gamepad attribute MUST be null" — For us: every action reachable by hands must use `select`/`squeeze` events, not gamepad polling.
- **Spec inconsistency: §3 says XR gamepads MAY appear in `navigator.getGamepads()`, §3.1 says MUST NOT** — same — verified yes — (paraphrase) — For us: always read gamepads from `XRInputSource.gamepad`, never from `navigator.getGamepads()`.
- **Quest Touch Plus registry mapping: [4] A/X, [5] B/Y, [6] thumbrest, [7] menu (left controller only); axes[0,1] empty** — Immersive Web CG, WebXR Input Profiles registry, `meta-quest-touch-plus.json` (fallbacks oculus-touch-v3, oculus-touch), https://github.com/immersive-web/webxr-input-profiles (raw JSON opened) — verified yes (registry, not a W3C spec) — "meta-quest-touch-plus" — For us: the left ≡ menu button may reach the page as buttons[7]; check on the headset with tools/xr-probe.html before using it (e.g. for a settings sheet).
- **Gamepad API: Working Draft, 10 July 2025; haptics there are `vibrationActuator.playEffect('dual-rumble'…)`; `hapticActuators[].pulse(value, ms)` lives only in the undated Gamepad Extensions draft** — W3C "Gamepad" https://www.w3.org/TR/gamepad/ and "Gamepad Extensions" https://w3c.github.io/gamepad/extensions.html — verified yes — "A GamepadHapticActuator object that represents the device's primary vibration actuator." — For us: `pulse()` is a non-standard-track extension; keep haptics optional and feature-detected.
- **Hand Input Module: Working Draft, 5 June 2024; 25 joints; explicit consent at session start; profile "generic-hand-select"; pinch may mean both select and squeeze** — W3C, https://www.w3.org/TR/webxr-hand-input-1/ — verified yes (full) — "MUST ask for explicit consent from the user at session creation time." — For us: agrees with headset-capabilities.md (25 joints); requesting hands adds a permission prompt to entry.
- **Layers API Level 1: Working Draft, 11 Aug 2026; projection/quad/cylinder/equirect/cube layers; static quad layers can be sharper for text; setting both `baseLayer` and `layers` throws** — W3C, https://www.w3.org/TR/webxrlayers-1/ — verified yes (read 200k of 258k) — "If both newState's baseLayer and newState's layers are set, throw a NotSupportedError" — For us: consistent with our note that requesting `layers` with A-Frame's base layer fails; a quad layer is the standard route to crisper clipboard text later.
- **AR Module: CR Draft 25 Apr 2025 (CR Snapshot 1 Nov 2022)** — publications page above — verified yes — (paraphrase) — For us: `immersive-ar` is the most mature MR piece.
- **Hit Test: WD 11 Dec 2025; entity types point/plane/mesh, default plane; not for virtual objects** — W3C, https://www.w3.org/TR/webxr-hit-test-1/ — verified yes — (paraphrase) — For us: real-surface placement only; our laser on virtual things stays our own raycast.
- **Anchors: Editor's Draft 27 Apr 2026 (Rec-track intent), persistent anchors by UUID, UA may delete them any time** — W3C IWWG, https://immersive-web.github.io/anchors/ — verified yes — "is intended to become a W3C Recommendation" — For us: our "max 8 per site" (headset-capabilities.md) is a Meta limit, not in the spec; never rely on an anchor surviving.
- **Plane Detection: Editor's Draft 30 Mar 2026; orientation, polygon, semantic label from a separate registry** — W3C IWWG, https://immersive-web.github.io/plane-detection/ — verified yes — (paraphrase) — For us: labels (table, wall…) can be null; always have a fallback.
- **Mesh Detection: Draft Community Group Report, 2 Feb 2026 (editor from Meta), `semanticLabel` nullable, values undefined** — W3C CG, https://immersive-web.github.io/real-world-meshing/ — verified yes — (paraphrase) — For us: not on the Recommendation track; treat as Meta-only.
- **Depth Sensing: WD 25 Aug 2026; cpu-/gpu-optimized; UA should ask consent** — W3C, https://www.w3.org/TR/webxr-depth-sensing-1/ — verified yes — (paraphrase) — For us: another permission prompt if used.
- **DOM Overlays: WD 24 Sep 2024; screen/floating/head-locked; examples are handheld AR** — W3C, https://www.w3.org/TR/webxr-dom-overlays-1/ — verified yes — (paraphrase) — For us: no basis for HTML UI inside the headset; the in-world clipboard remains the right path.
- **Lighting Estimation: WD 11 Dec 2025; spherical harmonics, main light, reflection cube map; low detail by default for privacy** — W3C, https://www.w3.org/TR/webxr-lighting-estimation-1/ — verified yes — (paraphrase) — For us: MR rooms only, optional.

## 2. W3C XR Accessibility User Requirements (XAUR) — read in full

W3C APA WG, "XR Accessibility User Requirements", Working Group Note, 25 Aug 2021, https://www.w3.org/TR/xaur/ — verified yes (read twice; the listed editor's draft w3c.github.io/apa/xaur/ returns 404, so the 2021 Note is the latest). It is a Note, not a standard; it has no numbers. Full list of requirements (19 user needs):

- **REQ 1a–1e Immersive semantics: describe locations/objects to assistive tech; remappable, repositionable, resizable controls with sensitivity; identify important objects; filter/sort; query objects for detail** — verified yes — (paraphrase) — For us: 1b backs a controls/sensitivity setting.
- **REQ 2a–2c Motion-agnostic interaction: act without physical movement; all UI reachable with one input method; several inputs at once** — verified yes — "Allow the user performing an action in the environment" — For us: every room must be finishable without walking, bending or reaching (seated mode).
- **REQ 3a–3b Personalisation: symbol sets; turn off or mute non-critical animations, sounds, messages** — verified yes — (paraphrase) — For us: the sign's hum and flicker need an off switch.
- **REQ 4a–4d Targets: no fine motor control; large, spaced targets; no simultaneous actions; sticky (serialised) multi-button input** — verified yes — (paraphrase) — For us: our one-press laser fits; never require trigger+grip together.
- **REQ 5a–5b Voice commands** — verified yes — (paraphrase) — For us: not planned; note as a gap.
- **REQ 6a High-contrast skins** — verified yes — (paraphrase) — For us: a high-contrast clipboard option.
- **REQ 7a–7b Magnification: check view context, reset focus; menus enlarge and reflow** — verified yes — (paraphrase) — For us: a "larger text" option must reflow onto more sheets, never shrink (as decisions.md already says).
- **REQ 8a Critical alerts detectable without moving focus** — verified yes — (paraphrase) — For us: low relevance.
- **REQ 9a–9c Gestures for blind users, self-voicing menus, remappable gestures** — verified yes — (paraphrase) — For us: our voice reading the sheet is partial self-voicing; gap otherwise.
- **REQ 10a–10b Sign-language avatar; signing video ≥ 1/3 of the video stream** — verified yes — (paraphrase) — For us: gap; low priority.
- **REQ 11a "Safe place" reachable by a shortcut** — verified yes — (paraphrase) — For us: the exit sign / "leave" flow is our safe harbour; a controller shortcut would complete it.
- **REQ 12a Time-limit alarms / digital wellbeing** — verified yes — (paraphrase) — For us: low priority.
- **REQ 13a–13c Reset/calibrate orientation device-independently; personalisable field of view; clear landmarks** — verified yes — "Ensure the user can reset and calibrate their orientation/view in a device independent way." — For us: offer an in-game recenter, not only the Meta button.
- **REQ 14a–14c Second-screen / braille output** — verified yes — (paraphrase) — For us: gap.
- **REQ 15a–15d Speed: change travel and interaction speed; extend timings; help; clear start/stop** — verified yes — "Allow users to change the speed they can travel" — For us: smooth-move speed and any timed step must be adjustable.
- **REQ 16a–16b Sickness triggers: avoid seizure/motion-sickness interactions and give alternatives; keep flicker minimal, under three per second, or let users reduce or turn it off** — verified yes — "This may be triggered when doing teleportation or other movements in XR." (UN16; 16b reads "Ensure flickering images are at a minimum, will not trigger seizures") — For us: XAUR names teleport itself as a possible trigger; offer choices, not one "safe" mode; add a flicker-off option.
- **REQ 17a–17b Spatial audio; text descriptions of important audio** — verified yes — (paraphrase) — For us: caption important non-speech sounds.
- **REQ 18a Mono audio to both ears** — verified yes — (paraphrase) — For us: our gaze cues use spatial sound; a mono option is needed for one-sided hearing.
- **REQ 19a–19b Captions/subtitles; customisable, context-sensitive reflow, possibly in a smaller area than TV** — verified yes — (paraphrase; 19 has no numbers) — For us: no placement or size rule exists in XAUR; it points to the Immersive Captions CG.

## 3. WCAG 2.2 criteria that carry over to XR

W3C, "Web Content Accessibility Guidelines (WCAG) 2.2", W3C Recommendation (2.2 first published 2023 per Jordan & Vanderheiden; current dated version 12 Dec 2024), https://www.w3.org/TR/WCAG22/ — verified yes (read all success criteria and the glossary terms below).

- **SC 2.3.1 Three Flashes or Below Threshold (A): nothing flashes more than 3 times in any 1 s, unless below the general and red flash thresholds** — verified yes — "flashes more than three times in any one second period" — For us: the rule our tests/glow.test.mjs guards.
- **General flash = a pair of opposing changes in relative luminance of ≥ 0.1 (10% of max) where the darker state is < 0.80; red flash = a transition to/from saturated red, R/(R+G+B) ≥ 0.8, with a chromaticity change > 0.2 in CIE 1976 UCS (new in 2.2)** — WCAG 2.2 glossary — verified yes — (paraphrase) — For us: the 0.1 and 0.80 are in relative luminance, not in our lamp level (see Conflicts).
- **Area exemption: concurrent flashes ≤ 0.006 sr within any 10° field (25% of it; about 341 × 256 px on a 1024 × 768 screen at 22–26 in)** — WCAG 2.2 glossary + Understanding 2.3.1 (updated 17 Sep 2025), https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html — verified yes — "for information purposes only, no endorsement implied" (on Harding/PEAT tools) — For us: the sign spans about 38° × 6° from the arrival spot (my estimate from scene.js and the test's eye point), far above 0.006 sr, so the exemption could not apply anyway.
- **SC 2.3.2 (AAA) no more than 3 flashes at all; SC 2.3.3 (AAA) interaction-triggered motion can be turned off** — WCAG 2.2 — verified yes — "Motion animation triggered by interaction can be disabled" — For us: the clipboard glide and teleport fades are interaction-triggered motion; a "reduce motion" option meets 2.3.3.
- **SC 2.2.2 Pause, Stop, Hide (A): moving/blinking content that starts by itself, lasts > 5 s and runs alongside other content must be pausable, unless essential** — WCAG 2.2 + Understanding 2.2.2, https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html — verified yes — "Five seconds was chosen because it is long enough to get a user's attention" — For us: the sign play runs alone before any text, so it is outside 2.2.2 as built; if it ever runs while the clipboard is readable, it needs a stop.
- **SC 1.4.2 Audio Control (A): audio playing automatically > 3 s needs pause/stop or its own volume control, independent of system volume** — WCAG 2.2 + Understanding 1.4.2 — verified yes — "If any audio on a web page plays automatically for more than 3 seconds," — For us: the looping sign hum fails this today unless the game gives an effects volume/mute.
- **SC 1.4.3 Contrast (AA): text 4.5:1, large text 3:1; large = 18 pt or 14 pt bold** — WCAG 2.2 — verified yes — "with at least 18 point or 14 point bold" — For us: agrees with vr-checklist (4.5:1).
- **SC 1.4.11 Non-text Contrast (AA): UI components and needed graphics 3:1 against adjacent colours** — WCAG 2.2 — verified yes — "adjacent color(s)" — For us: answer-button borders, the laser and its hit dot need 3:1; not in our checklist.
- **SC 2.5.8 Target Size Minimum (AA): 24 × 24 CSS px or spacing of a 24 px circle; SC 2.5.5 (AAA) 44 × 44** — WCAG 2.2 — verified yes — "at least 24 by 24 CSS pixels" — For us: with a CSS px = 0.0213°, 24 px ≈ 0.51° and 44 px ≈ 0.94°; our 2.5° targets exceed both.
- **CSS reference pixel = visual angle of about 0.0213°** — WCAG 2.2 glossary — verified yes — "visual angle of about 0.0213 degrees" — For us: the only standard bridge from WCAG pixels to degrees in a headset (18 pt ≈ 24 px ≈ 0.51°).
- **SC 2.2.1 Timing Adjustable (A): any time limit can be turned off, or adjusted to ≥ 10× the default, or extended** — WCAG 2.2 — verified yes — "at least ten times the length of the default setting" — For us: any timed answer in a room must offer this unless the timing is the experiment itself (then say so in the debrief).
- **SC 1.2.2 Captions (Prerecorded) (A); SC 1.4.12 Text Spacing (AA): line 1.5×, paragraph 2×, letter 0.12×, word 0.16×** — WCAG 2.2 — verified yes — (paraphrase) — For us: spacing values reappear in XAG 101.

## 4. Photosensitivity: broadcast and ISO rules

- **ITU-R BT.1702-3 (11/2023, in force): harmful flash = opposing luminance changes of ≥ 20 cd/m² when the darker image is < 160 cd/m² (Michelson 1/17 above 160, HDR only); any transition to/from saturated red; a sequence is not permitted when flashes cover > 25% of the screen AND > 3 flashes (6 changes) occur in any 1 s** — ITU-R, "Guidance for the reduction of photosensitive epileptic seizures caused by television", BT.1702-3, https://www.itu.int/rec/R-REC-BT.1702-3-202311-I/en (free PDF) — verified yes (all 12 pages read) — "Isolated single, double, or triple flashes are acceptable" — For us: same 3-per-second core as WCAG.
- **BT.1702-3 spacing: flashes whose leading edges are ≥ 334 ms apart (60 Hz) or ≥ 360 ms (50 Hz) are acceptable regardless of brightness or area** — same, Guideline 1 — verified yes — "separated by 334 ms or more are acceptable in a 60 Hz environment" — For us: a simple design rule for any blinking lamp: ≥ 334 ms between flash onsets.
- **BT.1702-3 cumulative risk: compliant flashing lasting more than 5 s may still be risky** — same — verified yes — "a sequence of flashing images lasting more than five seconds might constitute a risk" — For us: the starter flicker (about 1.5–4.9 s) is just under this; nothing in our test guards total flicker duration.
- **BT.1702-3 patterns: > 5 light/dark stripe pairs are potentially harmful over > 40% of the screen (stationary) or > 25% (moving/flashing)** — same, Attachment 1 to Annex 1 — verified yes — (paraphrase) — For us: tiling, blinds, ceiling grids and stripes near the eyes need a check.
- **BT.1702-3 viewing environment: risk rises in a darker room, on a brighter or larger screen, and closer to it** — same, Annex 5 — verified yes — "if viewed in a darker room; on a brighter or larger screen" — For us: a headset is all three at once; keep our stricter-than-TV stance.
- **Ofcom (UK) Broadcasting Code Rule 2.12 and Annex 1 "Guidance Note on flashing images and regular patterns"** — Ofcom, Section 2 Guidance Notes, https://www.ofcom.org.uk/__data/assets/pdf_file/0023/104657/Section-2-Guidance-Notes.pdf — verified NO (Ofcom returns HTTP 403 to every fetch; the archive is blocked). Values only via Jordan & Vanderheiden 2024 Table 1: 20 cd/m² below 160 cd/m², > 3 flashes/s unless leading edges ≥ 9 frames apart, > 25% of screen, saturated red — (no quote) — For us: same thresholds as BT.1702; no independent check.
- **ISO 9241-391:2016 (requirements, analysis and compliance tests for photosensitive seizures); applies to image content regardless of device; clauses on flashes, rapid image changes, red flashes, cumulative risk, prior warning, regular patterns; revision ISO/AWI 9241-391 registered Dec 2024** — ISO/TC 159/SC 4; scope and contents read in the Slovak national preview (STN EN ISO 9241-391, https://normy.normoff.gov.sk/norma/123081/nahlad) — verified partly (scope + table of contents; thresholds paywalled) — "designed to be applied to image contents" — For us: thresholds per Jordan & Vanderheiden: same 20/160 cd/m², 25%, > 3/s, and flicker above 65 Hz exempt.
- **Jordan & Vanderheiden 2024: compares Ofcom, NHK/JBA, ISO 9241-391, ITU-R BT.1702, WCAG; no guideline says how fast a transition must be; proposes 66 ms as the longest qualifying transition, 20 ms synchrony, merge flashes ≤ 15 ms apart, and the WCAG area rule (0.006 sr per 10°) for VR because 25% of a headset view is huge** — J. B. Jordan & G. C. Vanderheiden, "International Guidelines for Photosensitive Epilepsy: Gap Analysis and Recommendations", ACM TACCESS 2024, doi 10.1145/3694790, https://pmc.ncbi.nlm.nih.gov/articles/PMC11872230/ — verified yes (full text) — "No guidelines specify the timeframe over which a flash transition may occur." — For us: our 0.75 s ramp claim is the paper's own example ("does not look like a flash"); its working limit is 66 ms, so our ramps are far on the safe side.
- **XAG 118 Photosensitivity: flash = 10% luminance change with darker < 0.8; fail at about > 3/s over about 20% of the screen; red uses the old WCAG 2.0 formula (R−G−B)×320 > 20; patterns fail above 10% contrast over about 20%** — Microsoft, Xbox Accessibility Guideline 118, https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/118 — verified yes — "approximately 20 percent or more" — For us: Xbox uses a stricter area (20%) and an outdated red formula; WCAG 2.2 / ISO are the ones to follow.
- **GAG "Avoid flickering images and repetitive patterns": no flashing sequences > 5 s; > 3 flashes/s over ≥ 25%; moving patterns ≥ 25%, static ≥ 40%; never label a setting "epilepsy safe"; extra caution in VR** — gameaccessibilityguidelines.com, https://gameaccessibilityguidelines.com/avoid-flickering-images-and-repetitive-patterns/ — verified yes — "Particularly in VR, as the 25%/40% above is based on a typical screen display" — For us: name the toggle by what it does ("lamp flicker"), not "epilepsy safe".
- **People with photosensitive epilepsy name 12 VR barriers in 4 groups (equipment, interfaces/content, specific apps, individual sensitivity)** — L. South, C. Yildirim, A. Pavel, M. A. Borkin, "Barriers to photosensitive accessibility in virtual reality", CHI 2024, doi 10.1145/3613904.3642635, https://vis.khoury.northeastern.edu/pubs/South2024BarriersPhotosensitiveAccessibility — verified partly (abstract; the OSF PDF returned HTTP 500) — (no quote) — For us: supports customisation and warnings over a single global setting.

## 5. ISO/IEC and IEEE VR comfort and safety standards

- **ISO 9241-394:2020 (confirmed 2025): requirements for image content and displays to reduce visually induced motion sickness (VIMS); applies to VR HMDs, not AR see-through; clauses on visual rotation in passive and active viewing, large-field images and VR HMDs (5.3.4), Annex D methods of alleviating VIMS, Annex F head-tracking delay measurement** — ISO/TC 159/SC 4, https://committee.iso.org/standard/73227.html; contents read in the Slovak preview https://normy.normoff.gov.sk/norma/134996/nahlad — verified partly (scope + table of contents; numbers paywalled) — "virtual reality (VR) type of head mounted displays (HMDs)" — For us: the standard that governs our case exists but its limits (e.g. rotation speeds) are unread; do not quote numbers from it.
- **ISO 9241-392:2015 (confirmed 2021, review opened 2026): reducing visual fatigue from stereoscopic images incl. stereoscopic HMDs; clauses on interocular misalignment, luminance/contrast/chromatic differences, crosstalk, accommodation–convergence mismatch; numbers only in informative Annex C** — ISO/TC 159/SC 4, https://committee.iso.org/standard/60317.html; contents in the Slovak preview https://normy.normoff.gov.sk/norma/125274/nahlad — verified partly (scope + contents) — "Annex C presents numerical criteria as an informative reference." — For us: vergence–accommodation conflict for the 1 m clipboard is a named factor (5.6); values unread.
- **ISO/IEC 5927:2024 AR/VR safety — guidance on safe immersion (time), set-up and use; visual aspects only, vection and physical motion named; consumer and enterprise** — ISO/IEC JTC 1/SC 24, Ed. 1, 16 Feb 2024, 26 pp., https://committee.iso.org/standard/81847.html — verified partly (abstract only) — (paraphrase) — For us: the only international AR/VR safety standard; session-length guidance unread.
- **IEEE 3079-2020 HMD-based VR sickness reduction technology (active; approved 24 Sep 2020, published 29 Apr 2021); per third-party scope: content design rules, sickness assessment framework, motion-to-photon latency and network requirements** — IEEE SA, https://standards.ieee.org/ieee/3079/7283/ — verified partly (IEEE page has a one-line scope; the WG draft server mentor/imat.ieee.org refused connections) — "Head-mounted display-based virtual reality sickness-reducing technology is defined." — For us: no number from it can be used. Working-group papers cite a 20 ms motion-to-photon target, but they are drafts and disagree (17 ms, 15 ms).
- **IEEE 2048 series (VR/AR): P2048.1 device taxonomy, P2048.5 environment safety, P2048.6 immersive user interface listed "in development"; only IEEE 2048.101-2023 (AR on mobile devices) found published** — SFS store listing https://store.sfs.fi/en/ieee-2048101-2023 (it shows "Withdrawn" and "Active" at once); WG pages 404 or refused — verified partly — (no quote) — For us: nothing in the 2048 series governs comfort or accessibility today.

## 6. Game Accessibility Guidelines (GAG) — VR-relevant items

Source: gameaccessibilityguidelines.com, full list (about 123 items in Basic/Intermediate/Advanced × Motor/Cognitive/Vision/Hearing/Speech/General), https://gameaccessibilityguidelines.com/full-list/ — verified yes (list and the pages below). Pages carry no dates.

- **Basic, Vision: "Avoid VR simulation sickness triggers": offer teleport and snap turn (30° cited), the player always controls the camera, narrow peripheral view during movement, fixed reference frame, steady horizon, no acceleration, no motion blur, steady frame rate (60/75/90 fps by platform) and < 20 ms latency, no forced fast head turns, talk of "comfort" not "sickness"; make the comfort options the default** — https://gameaccessibilityguidelines.com/avoid-vr-simulation-sickness-triggers/ — verified yes — (paraphrase) — For us: matches our teleport + snap default and vignette for smooth moving; the 20 ms figure has no cited source on the page.
- **Basic: remappable controls; adjustable control sensitivity; simple controls; UI usable with the gameplay input; separate volume for effects/speech/music; save all settings; describe accessibility features** — full list + https://gameaccessibilityguidelines.com/ensure-that-all-settings-are-saved-remembered/ — verified yes — "either at a game level or a platform level" — For us: whatever the movement settings are, they must persist across visits.
- **Basic, Hearing: subtitles for all important speech; no essential information by sound alone; clear subtitle presentation: ≥ 46 px at 1080p, ≤ 40 characters per line, 2 lines (3 rarely), solid or semi-opaque background, mixed case** — https://gameaccessibilityguidelines.com/if-any-subtitles-captions-are-used-present-them-in-a-clear-easy-to-read-way/ — verified yes — "Text is presented no smaller than 46px@1080p" — For us: pixel rules do not transfer to a headset; 40 characters and 2 lines do.
- **VR subtitles: no screen bottom in VR; best current approach is a hybrid: text near the source when in view, otherwise near the player with a direction arrow** — https://gameaccessibilityguidelines.com/provide-subtitles-for-all-important-speech/ — verified yes — (paraphrase) — For us: a voice line spoken while the player looks away from the clipboard needs a direction cue or must wait.
- **Basic, Vision: readable default font size: 28 px at 1080p, "a minimum rather than a target", from Amazon Fire TV 10-ft UI** — https://gameaccessibilityguidelines.com/use-an-easily-readable-default-font-size/ — verified yes — "a minimum rather than a target" — For us: no VR figure exists here.
- **Intermediate, Motor: "Do not rely on motion tracking of specific body types": wide range of heights incl. wheelchair, configurable head height in VR, alternatives to crouching/leaning, one-handed players** — https://gameaccessibilityguidelines.com/do-not-rely-on-motion-tracking-of-specific-body-types/ — verified yes — "not everyone has two working hands with ten working fingers" — For us: seated mode and a height adjustment are expected.

## Conflicts with our notes

1. **tests/glow.test.mjs measures lamp level, not relative luminance.** The header states WCAG's rule (changes of ≥ 10%, darker below 0.80), but the code applies it to the lamp's 0–1 mix fraction between `#3a2d1f` and `#ffe7b0` (lightbox.js `mix`). In WCAG relative luminance the same lamp gives: level 0 → 0.029, 0.13 → 0.064, 0.6 → 0.347, 0.8 → 0.553, 0.9 → 0.674, 1 → 0.815 (my computation with the WCAG 2.2 formula; script in scratchpad vr-research/tools/lum.mjs). Result today: every ending still passes, and in luminance the worst case is 1 flash per second (the lamp-level test also passes). But the guard has a blind spot: a flicker between lamp levels 0.85 and 1.0 is skipped by the test (darker ≥ 0.8) yet is a WCAG flash (L 0.61 → 0.815, change 0.2, darker < 0.8). Fix: count in relative luminance.
2. **"brightness rising over 0.75 s does not read as a flash (Jordan & Vanderheiden 2024)" in sign.js** is the paper's illustrative example, not a threshold; the paper's working value is 66 ms. Not wrong, only conservative; cite 66 ms if a number is needed.
3. **"the small-area exception is not used (Jordan & Vanderheiden 2024)" in glow.test.mjs** agrees in effect: the paper recommends the small WCAG area rule (0.006 sr per 10°) for VR, not 25% of the screen; and the sign (~38° × 6° from the arrival spot, plus the point light on the walls) would exceed it anyway.
4. **No guard on total flicker duration.** BT.1702-3 and GAG warn about flashing sequences longer than 5 s even when compliant. The starter flicker runs about 1.5–4.9 s and ".com" blinks 9.9–12.9 s, so we are within it today, but no test keeps it so.
5. **vr-checklist "Subtitles for all speech, or playable without sound" is satisfied as written (Meta VRC .1), but XAG 104 / GAG / XAUR ask more:** speaker identification, captions for important non-speech sounds with direction, subtitles settable before any sound plays, size up to 200%, background opacity. Not a contradiction; a gap.
6. **vr-checklist "Contrast at least 4.5:1"** agrees with WCAG 1.4.3 and XAG 102, but omits WCAG 1.4.11 (3:1 for UI components: button borders, laser, hit dot) and XAG 102's high-contrast mode (7:1).
7. **The looping sign hum vs WCAG 1.4.2 (Level A):** audio auto-playing > 3 s needs a stop or its own volume control. No such control exists yet.
8. **decisions.md smooth moving "1.4 m/s at once"** is a fixed speed; XAUR REQ 15a asks that travel speed be changeable. Meta's default is not contradicted, but the standard asks for an option.
9. **headset-capabilities.md lists anchors, plane, mesh, depth, hit test, hands, layers without status.** None is a W3C Recommendation: mesh detection is only a Community Group draft (editor from Meta), anchors and plane detection are Editor's Drafts, the rest Working Drafts. "Persistent anchors (max 8 per site)" is not in the Anchors spec (Meta limit; unverified here).
10. **decisions.md "standing (Meta's 1 × 1 m stationary boundary)"** vs Meta VRC.Quest.Accessibility.9, which defines standing apps as usable within 7 ft × 5 ft (2.13 × 1.52 m). Different Meta documents; flag for the Meta researcher.
11. **Numbers that agree:** WCAG 2.3.1 "3 flashes per second" (vr-checklist) — agrees with WCAG, ISO 9241-391, BT.1702-3; sign colours are not saturated red (R/(R+G+B) = 0.39 lit, 0.43 unlit; limit 0.8) — agrees; 25 hand joints — agrees; targets ≥ 2.5° and letters ≥ 1.2° — above WCAG's 24 CSS px ≈ 0.51° and 18 pt ≈ 0.51°; `local-floor` with `local` fallback — agrees (fallback rarely needed); `requestSession` from a user gesture and pausing on visible-blurred/hidden — agree with the WebXR spec.

## Top 15 for our game (ranked)

1. **Flash rule in relative luminance** (WCAG 2.2 SC 2.3.1 + glossary; ISO 9241-391; BT.1702-3): ≤ 3 flashes in any 1 s, no saturated-red transitions, no area exemption in VR (Jordan & Vanderheiden 2024). Make the guard compute luminance (Conflict 1).
2. **A "lamp flicker / animation off" option** (XAUR 16b, XAG 117, GAG, WCAG 2.3.3): the sign lights steadily; name it by effect, never "epilepsy safe" (GAG).
3. **Total flicker ≤ 5 s per sequence and ≥ 334 ms between flash onsets** (BT.1702-3, GAG): add both to tests/glow.test.mjs.
4. **Hearing-independent play** (Meta VRC .1, XAG 104, GAG, XAUR 17b/19a): every spoken line as text, speaker named, important sounds captioned with a direction cue, subtitles available before the first sound.
5. **Sound control** (WCAG 1.4.2, GAG Basic, XAUR 3b/18a): separate volume/mute for effects (the hum), voice; a mono option.
6. **Locomotion choices with comfort defaults** (Meta VRC .8, GAG VR, XAUR 16a): teleport + snap by default; smooth moving and smooth turn as options; vignette with smooth moving, switchable.
7. **Adjustable travel speed and timings** (XAUR 15a/15b, WCAG 2.2.1, XAG 107 ±50%).
8. **Seated / fixed-position play** (Meta VRC .9, XAUR 2a, GAG body types): all interactions reachable seated; height adjustable.
9. **One-handed play** (Meta VRC .4, XAUR 4c/4d, XAG 107): either single controller can do everything; no simultaneous presses, no long holds.
10. **Turn and recenter without head movement** (Meta VRC .7, XAUR 13a): snap turn everywhere plus an in-game recenter.
11. **Contrast** (WCAG 1.4.3/1.4.11, XAG 102): 4.5:1 text, 3:1 UI parts, optional 7:1 high-contrast clipboard; measure against the worst background patch.
12. **Text size options** (XAG 101 200%, XAUR 7b, Meta VRC .2): larger text reflows onto more sheets, never shrinks.
13. **Not colour alone** (XAG 102, Meta VRC .6, GAG): pair colour with shape/pattern/label (levers).
14. **Input facts** (WebXR Gamepads xr-standard; Input Profiles registry): stick on axes[2]/[3], stick click buttons[3]; system button never exposed; left menu maybe buttons[7] — probe before use; hands give no gamepad, use `select`.
15. **Persist every setting** (GAG Basic) and read them before the opening plays.
