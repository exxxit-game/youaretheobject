## 1. What Quest Browser supports in WebXR `immersive-ar`, today

- **Browser versions now follow Chromium milestones** — Meta, "Browser Developer Release Notes", developers.meta.com/horizon/documentation/web/browser-release-notes/ (latest entries 144 → 146.0 Apr 2026 → 149.1 → 150.1 Aug 2026) — verified yes — "updated to Chromium Milestone 146" (146.0) — For us: "browser 152" in our probe notes is plausible under this scheme; record the full UA string next to every probe result.
- **Passthrough (`immersive-ar`)** — Meta, "Mixed Reality Support in Browser" (webxr-mixed-reality page; written for Quest 2/Pro, Connect 2022, not updated for Quest 3) — verified yes — "You must draw your content on a transparent background" — For us: MR = a second session mode; every pixel we draw opaque hides the real room.
- **Pages never see passthrough pixels inside `immersive-ar`** — W3C WebXR AR Module L1 (CR Draft 25 Apr 2025; ED 25 Apr 2025) §3 and the Meta page above — verified yes — "MUST NOT expose camera images to the content" — For us: an MR room cannot record or analyse the player's room through WebXR; good for privacy, rules out camera-based measures there.
- **Blend modes: one session can look fully virtual or fully real** — W3C AR Module §2.2/2.4 — verified yes — "Alpha determines how much of the real world shows through" (paraphrase of §2.4; spec text: output composited "on top of buffers containing pixel representations of the real-world environment") — For us: inside one `immersive-ar` session we can fade from our virtual corridor to the real room by alpha, with no new session and no button press (see Conflicts).
- **Plane detection (Space Setup data)** — Meta MR page; W3C Plane Detection ED 30 Mar 2026 (immersive-web.github.io/plane-detection/) — verified yes — "always horizontal or vertical rectangles on Meta Quest headsets" — For us: tables, walls, floor arrive as labelled rectangles (`semanticLabel`); good enough to put an apparatus on the real table.
- **No room scan → no planes; `initiateRoomCapture()`** — Meta MR page; Plane Detection ED §4.1 — verified yes — "few people run guardian's space setup" — For us: wait 2–3 s after session start, then call it once per session if `detectedPlanes` is empty; always have a fallback.
- **Mesh detection (room mesh + labelled boxes)** — W3C Mesh Detection, Draft CG Report 2 Feb 2026 (immersive-web.github.io/real-world-meshing/); IWSDK Ch. 11 "Scene Understanding" (v0.5.3, updated 22 Jul 2026); Meta Help "Manage website permissions…" (meta.com/help/quest/1406582186767703) — verified yes — "Available only on Quest 3 and Quest 3S" (Meta Help, mesh data) — For us: real furniture as colliders; still a Community-Group draft, not a W3C track spec.
- **Anchors and persistent anchors** — Meta MR page; W3C Anchors ED 27 Apr 2026 — verified yes — "can currently only create 8 persistent anchors at a time" — For us: enough for "the apparatus stays on your table next time"; lost in private mode and when site history is cleared.
- **Hit test against real surfaces without a room scan** — UploadVR, D. Heaney, 10 Oct 2025 (Horizon Browser 40.4); IWSDK Ch. 14 "Environment Raycast" — verified yes (press + Meta SDK docs; no Meta release note found) — "now uses Meta's Depth API under the hood" — For us: tap-to-place works for players without Space Setup; depth works to about 5 m (UploadVR).
- **Depth sensing → real-world occlusion** — W3C Depth Sensing ED 25 Aug 2026; IWSDK Ch. 15 "Depth Occlusion" (4 Sep 2026); Meta release note 146.0 (21 Apr 2026) "Experimental WebGPU and WebXR depth projection support" — verified yes — "MUST be provided when depth-sensing is included" (spec, about the `depthSensing` init dictionary) — For us: occlusion by the player's own hands, pets, furniture; depth is ML-estimated and weak on thin, transparent, reflective things (Meta Health "Depth", updated 11 Mar 2026).
- **Spatial permission prompt (planes + depth merged)** — Wikipedia "Meta Quest Browser" version table, 36.2 (16 Dec 2024), citing Meta release notes 36.2 — verified no (secondary; Meta's page now lists only the last 10 releases) — "combined into single 'Spatial' permission" — For us: the player sees one "Spatial data" prompt; Meta Help confirms a notice appears and can be declined.
- **Hand tracking in WebXR** — Meta "WebXR Hands" (developers.meta.com/horizon/documentation/web/webxr-hands) — verified yes — "exposes the poses of the 25 skeleton joints" — For us: left-hand palm pinch is reserved and exits the session, so no room may ask for "look at your palm and pinch".
- **Headset (passthrough) cameras for websites — via getUserMedia, not WebXR** — Meta Help "Manage website permissions for immersive web experiences" (1406582186767703) — verified yes — "real-time Passthrough camera feed from the front of your headset" — For us: a separate "Headset cameras" permission gives a site the live front-camera feed plus intrinsics; one site at a time; pauses when minimised. IWSDK Ch. 13 "Camera Access" (4 Sep 2026) builds on MediaDevices. Version: forum reports say 38.2 "initial support" (May 2025), all users from 40.1 (Sept 2025) — Babylon.js forum thread 58274, verified no for the version numbers.
- **WebXR Raw Camera Access (`camera-access`)** — W3C Raw Camera Access, Draft CG Report 11 Dec 2025 — verified yes for the spec; Quest support: a Meta community-forum post reports "not supported for mode: immersive-ar" on Horizon OS v85 — verified no (page returned 403) — For us: no per-frame camera image aligned to the eyes in Quest WebXR; getUserMedia is the only camera route.
- **Lighting estimation** — W3C Lighting Estimation ED 11 Dec 2025 — verified yes for the spec; Quest support: no Meta document lists it; A-Frame maintainer on issue #5524 (2024): only Chrome Android — verified no — For us: assume no real-room light estimate; light our objects by hand; probe it once.
- **Boundary in `immersive-ar`** — no Meta web document found; Meta native docs say boundary suppression needs the native SDK — verified no — For us: our probe already saw `bounded-floor` in MR; whether the grid shows during a browser MR session is unchecked (Gaps).
- **What Meta does not control after a site gets the data** — Meta Help 1406582186767703 — verified yes — "should only allow access to this data on websites that you trust" — For us: privacy duty is entirely ours; say it in privacy.html.

## 2. A-Frame 1.7.x and AR

- **AR button is hidden by default** — A-Frame 1.7.1 docs `xr-mode-ui` (raw docs at tag v1.7.1); issues #5533, #5436, #5402 — verified yes — "XRMode … vr" (default value in the docs table) — For us: set `xr-mode-ui="XRMode: xr"` or our own button calling `enterAR()`.
- **`ar-mode` state, background removed in AR** — vendored `vendor/aframe-1.7.1.min.js` (read): in `ar-mode` the scene background is set to null while rendering; `enter-vr` fires for both modes — verified yes (source) — no quote — For us: rooms must check `sceneEl.is('ar-mode')`; `hide-on-enter-ar` hides sky/floor.
- **Plane + mesh: `real-world-meshing` (since 1.5.0, 14 Nov 2023)** — A-Frame CHANGELOG and docs — verified yes — "requires a browser with support for the WebXR Mesh Detection Module" — For us: it adds `mesh-detection` and `plane-detection` to *required* features (source), so a player who declines the Spatial prompt gets no session at all — we would write our own optional version.
- **Anchors: `anchored` (since 1.5.0), `persistent: true` uses requestPersistentHandle** — A-Frame docs + source — verified yes — "If the anchor persists on page reloads. The entity must have an id." — For us: usable as is.
- **Hit test: `ar-hit-test`** — A-Frame docs; CHANGELOG 1.7.1 fix "Initialize on enter-vr" — verified yes — no quote — For us: it adds `hit-test` and `anchors` as optional; known issue #5358 (disable after placing loses track, open).
- **Depth occlusion is built into the bundled three.js but A-Frame cannot request it** — source of `vendor/aframe-1.7.1.min.js`: three's WebXR manager writes real depth into the depth buffer when `depth-sensing` is `gpu-optimized`; A-Frame's `webxr` system passes only requiredFeatures, optionalFeatures, domOverlay to requestSession — verified yes (source + spec) — no quote — For us: we must add `depthSensing: {usagePreference:['gpu-optimized'], dataFormatPreference:[...]}` to `sceneEl.systems.webxr.sessionConfiguration` ourselves, else the spec says the optional feature is silently ignored.
- **Lighting: `reflection` component asks for `light-estimation`** — A-Frame source/issue #5524 — verified yes — no quote — For us: harmless on Quest, but do not rely on it.
- **IWSDK (Meta's own web SDK, v0.5.3) as the reference implementation** — IWSDK guides 11/13/14/15 — verified yes — "environment raycasting does not require room scanning" — For us: copy its feature choices (planes, meshes, anchors, hit-test, depth gpu-optimized, camera via MediaDevices); not a reason to leave A-Frame.

## 3. Meta mixed-reality design guidelines (read in full: Overview, Key considerations, Passthrough, Scene, Spatial anchors, Health & safety + Depth/Passthrough/Scene/General, Boundaryless, Comfort, Privacy, Splash screen)

- **Start from the physical world; objects grounded and true to size** — Meta "Key considerations" (design/mr-design-guideline, 7 Oct 2025) — verified yes — "arranged to match the size and depth of reality" — For us: an MR apparatus must sit on the real table at real size, with a shadow.
- **Always have a fallback when the furniture is missing** — same page — verified yes — "make sure to have alternative options" — For us: every MR room needs "no table / small room" variants.
- **Design for a minimally viable environment** — same page — verified yes — "Determine the minimum space and surface requirements" — For us: matches our space tiers; add "needs a table / a free wall".
- **Content at about 1 m, slightly below eye line; nothing appears suddenly close** — same page — verified yes — "roughly 1 meter distance slightly below the user's line of sight" — For us: same as our VR panel rule.
- **No teleport in MR** — same page — verified yes — "do not use teleport to move the user or other content" — For us: the corridor's teleport and snap turn must be off whenever passthrough is visible.
- **Never put virtual things behind a real wall or inside furniture** — same page; Health "Depth"; "Boundaryless" (4 Sep 2026) — verified yes — "Do not place virtual objects behind walls" — For us: room content must be clipped to the planes; a "portal" goes on the wall surface only with a buffer zone.
- **Minimise head-locked content in passthrough** — Key considerations; Depth page — verified yes — "Avoid locking HUD style content to the user's head movements" — For us: same as our world-locked text rule.
- **About half of players sit, half stand** — Key considerations — verified yes — "approximately half of users will play sitting down" — For us: every MR room playable seated.
- **Clearly mark reality transitions; blend smoothly; give time to reorient** — "Passthrough" (8 Oct 2025); Health "General" (4 Sep 2026) — verified yes — "provide time for users to reorient and adapt before introducing task demands" — For us: after corridor → real room, no timed task for the first seconds; matters for reaction-time rooms.
- **Overlapping incongruent realities is discouraged, except a 1:1 match** — Passthrough page — verified yes — "the effect can be magical" (about a 1:1 match) — For us: "your room re-skinned as the 1979 lab" only if aligned to the planes; otherwise a clean fade.
- **Users lose their mental map after VR and must reorient back in passthrough** — Health "General" — verified yes — "quickly lose their mental map and need to reorient" — For us: an MR→VR→MR experiment (Liu/Kelly "new room") has this cost built in; measure it.
- **Portals on walls/floor: users reach in, feel a drop** — Health "General" — verified yes — "a sensation of dropping when users walk over portals placed on the floor" — For us: Juan & Perez pit only for seated or standing-still players, never while walking.
- **Boundary recommended at all times for fully immersive parts** — Health "General" — verified yes — "A boundary is recommended at all times for fully immersive experiences" — For us: a VR room inside an AR session still needs the play-area check.
- **Scene is not a safety feature; Space Setup ≠ smart boundary** — Health "Scene" (8 Oct 2025); Boundaryless page — verified yes — "ASC is not a safety feature" — For us: never tell the player the scan keeps them safe.
- **Depth limits** — Health "Depth" — verified yes — "limited accuracy beyond four meters" — For us: occlusion trustworthy only at arm's and room distances.
- **Dynamic things (pets, people) only with depth, not scene** — Health "Scene" — verified yes — "you should not create experiences that include dynamic physical objects without enabling Depth API" — For us: request depth for any MR room with a walking or reaching task.
- **Long full-passthrough exposure** — Health "Passthrough" (25 Jul 2025) — verified yes — "may result in visual discomfort, motion sickness, disorientation" — For us: keep MR rooms short (fits our ~10-min rule); offer breaks.
- **Passthrough periphery as a comfort tool** — Meta "Comfort" (17 Dec 2025) — verified yes — "provides stable visual references and helps ground the user" — For us: a "real room at the edges" option is a sourced alternative to our vignette.
- **Ask for permission in context, not at launch** — Meta "Designing for privacy" (6 Oct 2025) — verified yes — "Ask for permissions right after launching an app" (listed as a DON'T) — For us: request the Spatial / camera permission at the door of the MR room, with one line of why.
- **Splash in passthrough: art must work on light and dark rooms** — Meta "Splash screen best practices" (2 Mar 2026) — verified yes — "should work well on both light and dark backgrounds" — For us: the MR-room sign and sheet need an opaque backing (real rooms vary in light).
- **Lighting the room** — Meta "Lighting and effects" (27 Jun 2025) and "Passthrough" — verified yes — "Lighting passthrough is still an open area for exploration" — For us: dimming passthrough with a semi-transparent black layer is the sourced trick (e.g. dark-room conditions).

## 5. Research: perception, sickness, presence, MR as a lab

- **Passthrough is not natural vision: acuity and contrast loss, worse in dim rooms (Quest 3)** — Wang J. et al. 2026, arXiv 2601.02805 v2, "The Perceptual Cost of Passthrough", N=24, 572 vs 117 lux — verified yes (full) — "None of these VST HMDs can ensure normal visual acuity" — For us: no small text, low contrast or colour-only cues in MR; MR rooms need decent room light; Quest 3 contrast at 117 lux fell to the "visual disability" range.
- **Short passthrough exposure already causes sickness, body-schema change, distance underestimation, "social absence" (Quest 3)** — Santoso & Bailenson 2024, arXiv 2407.16904, N=40, 4 min in passthrough — verified yes (full) — "passthrough, even in short doses, can create simulator sickness" — SSQ total 26.87 vs 9.44 without headset; blind walking to 3.12 m: 8.85 cm more underestimation in passthrough; no aftereffect. For us: MR is not "the real room for free"; it is its own condition.
- **Field notes: distortion (~15% stretching), distance errors, sickness, others feel less present** — Bailenson et al. 2024, Technology, Mind, and Behavior 5(2), doi 10.1037/tmb0000129 (invited, qualitative, 11 authors, ~140 min each on Quest 3) — verified yes (full) — "lapses in judgments of distance, induce simulator sickness" — For us: any social MR room (proxemics, Asch-like) must expect weaker real-person presence.
- **Quest 3 passthrough makes people move cautiously: head rotation speed down four-fold** — Solbach et al. 2026, arXiv 2609.25002, N=110, block assembly — verified yes (full) — "a four-fold suppression of rotational head velocity" — (133.3 → 33.4 deg/s). For us: head-movement and search-time measures in MR are not comparable to VR or real-life norms.
- **Same Quest 3, VR vs passthrough MR: opposite pointing biases** — Wang X. M. et al. 2026, arXiv 2608.06132, N=40 (Quest Link) — verified yes (full) — "validate perceptuomotor interaction techniques separately in VR and MR-VPT" — MR overshot (+0.43 cm), VR undershot (−0.31 cm), VR adapted slower. For us: a room run in both modes needs its own baseline per mode.
- **Video see-through underestimates distance more than real viewing** — Pfeil et al. 2021, CHI (ZED Mini on Vive, blind throwing 3–5 m; already in folder) — verified yes (read header + results) — "causes a significant difference between normal, unrestricted viewing" — For us: supports a passthrough-vs-real-vs-VR distance room (catalog: philbeck-loomis-1997, jin-2021).
- **Virtual objects in Quest 3 passthrough are overestimated in blind walking** — Kenoyer-Healy, Sturgeon & Arefin 2026, IEEE TVCG 32(5), PMID 41955138 — verified no (abstract only) — "overestimated with Meta Quest 3" — For us: virtual-object distances in MR may err the other way from real-object distances.
- **Passthrough latency** — Optofidelity via MIXED, 16 Feb 2024 (min values; Vision Pro ~11 ms, Quest 3/Pro/XR Elite 35–40 ms) — verified yes for the article, Quest 3 exact value only in a chart — "latencies of 35 to 40 milliseconds" — For us: do not run fast reaction-time measures on what the player sees through passthrough without our own measurement (Santoso uses 39 ms; Bailenson says ~12 ms — see Conflicts).
- **Passthrough itself causes sickness; better reprojection reduces it** — El Chemaly et al. 2025, CHI, arXiv 2502.11497 (Android XR prototype, not Quest), N=25 — verified yes (full) — "significantly reduced nausea, disorientation, and total scores" — For us: MR sickness is a property of the device pipeline we cannot change; keep MR exposure short.
- **Quest 3 vs Vision Pro vs Varjo XR-3 passthrough comfort** — Vona et al. 2025, IEEE VR poster, arXiv 2502.06382, N=31 — verified yes (full, 3 pages) — "the Apple Vision Pro outperformed the Meta Quest 3 and Varjo XR-3" — Quest 3 CSQ-VR 12.68 vs AVP 9.68. Weak (poster).
- **Meta's update reduced passthrough warping (v66)** — Road to VR, S. Hayden, 5 Jun 2024 (Meta statement) — verified yes — "significantly reduce[s] image distortion in Passthrough" — For us: distortion findings before mid-2024 may overstate today's Quest 3.
- **Presence in MR has no validated measure** — Tran, Langlotz & Regenbrecht 2024, CHI, doi 10.1145/3613904.3642383, >320 studies — verified yes (full text read for method, discussion, conclusion; appendix table skimmed) — "could contribute to a looming replication crisis" — For us: do not claim "MR felt more real" from an IPQ score; use behaviour (e.g. smoke-room leaving rate) instead.
- **AR and VR pits gave similar presence and anxiety** — Juan & Pérez 2010 (already in folder; n=20, detectable d=.66) — verified yes — "we did not find differences between the systems" — For us: supports juan-perez-2010 card; small sample.
- **VR evacuation effects smaller than real room** — Kinateder & Warren 2016, Frontiers Robotics & AI 3:43 (in folder) — verified yes — "effect sizes in VR may be smaller than those in the real world" — 57% real vs 40% VR left overall; 26 of 50 alone participants left. For us: the open MR question in headset-capabilities.md is well founded.

## 6. Safety, consent, privacy in MR

- **What a web page can learn of the room** — W3C AR, Plane, Mesh, Depth, Hit-test, Anchors, Lighting specs (privacy sections, read); Meta Help 625635239532590 "Manage spatial data sharing" — verified yes — "Given a depth buffer with sufficiently high resolution" (depth spec warns it can approach camera detail) — Through WebXR: planes with labels, room mesh, depth maps, hit points, anchor poses; never camera pixels. Through getUserMedia (separate permission): live camera video.
- **What is stored, where** — Meta MR page (persistent anchors: per site, deleted with site history, not in private mode); Meta Help 625635239532590 (Space Setup kept on headset; "enhanced spatial services" send spatial data to Meta servers; user can clear physical-space history and delete server data) — verified yes — "Clear physical space history" — For us: we store nothing of the room; at most one anchor handle in localStorage.
- **Meta's developer data rules (store apps)** — Meta Developer Data Use Policy (updated 2 Jul 2026) — verified yes — "This includes data from sensors such as a microphone or camera" — Spatial data is not named; Device User Data may not be sold, used to identify a person, or kept when no longer needed. For us: binds us only if we ship a PWA to the Horizon Store; our rule should be stricter anyway.
- **Player consent for room data** — Van Bouwel (Road to VR 2023) — verified yes — "active consent of the player each time it is shared" — For us: never send room geometry with results; if ever needed for a bug, ask each time.

## 7. For us

**MR enables or improves**
- Table-top rooms where the original was a real table: Corsi blocks, Duncker candle box, Caljouw pouring, Stroop/flanker reach, Muayqil line bisection — passthrough + planes + hand tracking; seated.
- Rooms about the body in a real room: Kohnstamm (real wall), Rochat & Wraga reach, Aubert's "door" (real room vs dark), Wang & Spelke, Liu/Kelly spatial updating.
- A genuine new question: is passthrough perceived like reality or like VR (distance, smoke-room leaving rate, pit anxiety)? Santoso 2024, Solbach 2026 and Wang XM 2026 show MR is a third condition, so this is publishable, not a replay.
- The "break the wall / re-skin the room" wow moment (First Encounters, Starship Home) as a reveal device.

**MR breaks or weakens**
- Anything needing a controlled, identical scene for everyone (each room is different; lighting varies 117–572 lux matters — Wang 2026).
- Fast reaction-time measures on passthrough images (35–40 ms camera latency, unmeasured jitter); fine detail, small text, colour-only cues.
- Teleport / snap-turn locomotion (Meta: no teleport in MR); our corridor walk would have to be real walking or stay VR.
- Social rooms with a real co-present person (social absence: Santoso 2024).
- Big-space rooms in small rooms; floor portals for walking players.

**Costs**
- Players without Space Setup: no planes/mesh until they scan (Meta: "few people run" it); hit test now works without a scan (40.4), so design placement by hit test first, planes second.
- Permission prompts: "Spatial" (WebXR) and "Headset cameras" (getUserMedia); declining must still leave a playable room.
- A-Frame work: own optional plane/mesh code (the built-in one makes them required), manual `depthSensing` init, `XRMode: xr`, `ar-mode` branches.
- Every MR room must be tested on several room layouts (Laser Dance emulator) and in dim light.
- Ethics wording: the player's home is in view; say what we see (planes, not pictures) before the first MR room.

## Conflicts with our notes

1. `docs/headset-capabilities.md`, "Camera images … not available in Quest Browser WebXR … Not available to a web game (native apps only)": half wrong. WebXR `immersive-ar` indeed exposes no pixels (W3C AR module), but Meta Help documents a **"Headset cameras" website permission** giving the live front-camera feed with intrinsics via getUserMedia, and IWSDK v0.5.3 has a Camera chapter. Correct the row: "not in WebXR; yes via getUserMedia with its own permission".
2. Same file, "Switching between VR and mixed reality means ending one session and starting another, which needs a button press": only true if VR runs as `immersive-vr`. Inside one `immersive-ar` session, opaque rendering hides the room and alpha fades it back (W3C AR module §2.4; Meta "Passthrough" page recommends opacity blending). The VR corridor could run in an AR session and open onto the real room without a new session (needs a probe: performance, boundary behaviour). This also affects `objekt-files/notes/archive/docs/ideas/east-europe-global-south.md` §1 ("needs a new session and a button press").
3. Same file cites the Meta webxr-mixed-reality page as current: that page is written for Quest 2 / Quest Pro (Connect 2022) and its menu path "Settings > Boundary > Mixed Reality" is old; the current help pages say Space Setup lives under Environment setup. Facts still verified on it: 8 persistent anchors per site, private-mode loss, `initiateRoomCapture` once per session.
4. Same file, hit test "browser 40.4, Oct 2025": confirmed (UploadVR 10 Oct 2025); no Meta release note found for it.
5. "Room mesh … 22 meshes": consistent with Meta Help (mesh only on Quest 3/3S). But A-Frame's `real-world-meshing` makes mesh and plane detection *required*; our probe granting them does not mean A-Frame's component degrades gracefully.
6. "Smoke-alarm replication: real room 68% leaving alone, VR 36%": the paper's text gives 57% vs 40% overall and 26 of 50 alone participants leaving; 17/25 (68%) + 9/25 (36%) = 26 is consistent, but the split by environment is only in Figure 2 (not readable in the text file). Mark as "from the figure".
7. Source conflict, not ours: Quest 3 passthrough latency "about 12 ms" (Bailenson et al. 2024) vs "35 to 40 ms" (Optofidelity 2024, minimum values) vs "39 ms" (Santoso & Bailenson 2024). Use the measured 35–40 ms until we measure ourselves.
8. Santoso & Bailenson 2024 preprint has a reversed sentence on social presence (text says 2.48 without headset is "higher" than 3.08 in passthrough); the direction claimed (less social presence in passthrough) cannot be trusted from that sentence alone.

## Top 15 for our game (ranked)

1. MR is its own condition, not "real life": sickness after 4 min (SSQ 26.9 vs 9.4), distance underestimation, social absence (Santoso & Bailenson 2024); four-fold slower head turns (Solbach 2026). Every MR room needs its own baseline.
2. WebXR never gives camera pixels in `immersive-ar`; the room is known only as planes/mesh/depth (W3C AR module) — our privacy line; camera video is a separate getUserMedia permission we should not request.
3. One `immersive-ar` session can be fully virtual or fully real by alpha: the corridor → real-room transition can be a fade, not a session switch (W3C AR §2.4; Meta Passthrough page). Probe it.
4. No teleport in MR; give time to reorient after any VR↔MR change before a timed task (Meta Key considerations; Health General).
5. Placement first by hit test (works without a room scan since 40.4), planes/mesh only as an upgrade; always a "no table / small room" fallback (UploadVR 2025; Meta "alternative options").
6. Many players have no Space Setup ("few people run guardian's space setup"): call `initiateRoomCapture()` once, after 2–3 s, only if no planes (Meta MR page).
7. A-Frame 1.7.1 gaps: AR button off by default; `real-world-meshing` forces required features; `depth-sensing` needs a hand-added `depthSensing` init or it is ignored (A-Frame source + W3C Depth spec).
8. Ask for the Spatial permission in context at the MR room's door, never at launch, and keep the room playable if declined (Meta privacy design; Meta Help).
9. Never put content behind real walls or inside furniture; portals with a buffer; no floor portals for walking players (Meta Health Depth/General; Boundaryless).
10. Request depth for any MR room with reaching or walking (people/pets occlude correctly); trust it only within ~4 m, not on glass or thin things (Meta Health Depth).
11. Passthrough degrades acuity and contrast, much worse in dim rooms: big, high-contrast, non-colour-only cues; check room light (Wang 2026).
12. Do not time fast reactions to passthrough events (35–40 ms latency, Optofidelity); keep RT stimuli virtual.
13. Table-top rooms are the proven quiet MR form (Cubism, Corsi/Duncker/pouring cards); walls are steadier than tables as a canvas (Wall Town Wonders).
14. Test each MR room on several stored room layouts and body sizes (Laser Dance emulator); playtest in MR with hands (Cubism).
15. Presence questionnaires are not validated for MR (Tran 2024): compare MR vs VR by behaviour (leaving rate, distance walked, anxiety rating), not IPQ.
