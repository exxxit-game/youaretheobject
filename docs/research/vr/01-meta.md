## 1. Comfort and locomotion (Meta design guidelines)

- **Comfort-friendly locomotion first: teleport and snap turn, and customisable settings; avoid sudden acceleration and camera motion the user did not make** — Meta, "Comfort", 2025-12-17, https://developers.meta.com/horizon/design/comfort/ — verified yes — "Favor options like teleportation and snap turning, and offer customizable settings" — For us: corridor default stays teleport + snap; smooth is opt-in.
- **Teleport is the comfort option but may disorient; slide gives control but may sicken; let users choose** — Meta, "Locomotion user preferences", 2026-09-08, https://developers.meta.com/horizon/design/locomotion-user-preferences/ — verified yes — "It's important to let users choose between these two options" — For us: settings must offer both teleport and slide.
- **Snap turn angle choices: 30, 45 or 90 degrees** — same page — verified yes — "we recommend providing the following options: 30, 45, or 90 degrees" — For us: we have 45° only; add 30 and 90 as choices.
- **Smooth turn: let users adjust rotation speed** — same page — verified yes — "It is recommended to allow users to adjust the speed of the rotation" — For us: smooth turn needs a speed choice (we fix 180°/s).
- **Direction mapping for slide (head-relative, initial head-relative, hand-relative, initial hand-relative) is a user preference** — same page — verified yes — "it's crucial to allow users to choose their preferred mapping style" — For us: slide is head-relative now; a mapping choice is recommended, no default named by Meta.
- **Comfort assistance (blink, dash, vignette) belongs in user settings** — same page — verified yes — "We strongly advise incorporating comfort assistance into user settings" — For us: the vignette must be a setting (on/off at least), not only built in.
- **Preference menus: reachable during play (e.g. menu button), comfort defaults, switch live without restart, persist across sessions; preferences are per app** — same page, section "Implementing locomotion preferences" — verified yes — "Default to comfort-friendly options (teleport, snap turn)" — For us: this is the checklist for our settings page.
- **Walking speed ~3 mph / 1.4 m/s, running ~6 mph / 2.8 m/s** — Meta, "Locomotion comfort and usability", 2025-12-17, https://developers.meta.com/horizon/design/locomotion-comfort-usability/ — verified yes — "walking ~3 mph/1.4 m/s, running ~6 mph/2.8 m/s" — For us: our 1.4 m/s agrees (my arithmetic: 3 mph is 1.34 m/s; Meta rounds).
- **Minimise acceleration: quantized velocity (instant switch between fixed speeds), stepped translations, restrict axes (15/30/45/90/180°), stable camera height, soft camera collisions** — same page — verified yes — "setting fixed movement speeds ... and switching between them instantly" — For us: our instant 1.4 m/s with no ramp matches; walls should stop us softly, not abruptly.
- **Reduce optic flow: realistic speed, vignette, occluding geometry, plain textures** — same page and "Reduce Optic Flow", 2026-05-11, https://developers.meta.com/horizon/resources/locomotion-design-reduce-optic-flow/ — verified yes — "Vignettes ... darken or completely occlude the edges of the screen" — For us: the corridor's tiled walls and floor add optic flow during slide.
- **Keep walls at a distance; prefer forward movement; avoid strafing, back-stepping, continuous turning; avoid stairs/slopes** — Meta, "Locomotion virtual environments", 2025-12-17, https://developers.meta.com/horizon/design/locomotion-virtual-environments/ — verified yes — "Design environments with open spaces or large rooms that keep users away from walls" — For us: a narrow corridor is the hard case for smooth motion; teleport default is right.
- **Seated mode should be supported unless incompatible; user chooses seated/standing early; height defaults to system player height; artificial turning needed** — "Locomotion comfort and usability" (design version 2025-12-17; the older resources copy of 2024-12-18 lacks this section) — verified yes — "Seated mode is important for accessibility and should be supported" — For us: the corridor's "seated player lifted to standing eye height" fits; offer the seated/standing choice at the start.
- **Offer three locomotion presets: Recommended, Comfortable, Advanced** — Meta, "Locomotion Best Practices", 2025-12-17, https://developers.meta.com/horizon/design/locomotion-best-practices/ — verified yes — "Provide three main settings" — For us: a simple first screen could offer these three presets instead of many switches.
- **Consistent frame rate prevents judder; timewarp helps but is not a substitute** — "Locomotion comfort and usability" — verified yes — "maintaining a solid framerate is still essential" — For us: measure the heaviest corridor moment, not the average.
- **Three overarching musts: prevent visually induced motion sickness, photosensitivity (ISO 9241-391:2016), design for breaks** — Meta, "Overview of immersive VR apps best practices", undated, https://developers.meta.com/horizon/design/bp-overview/ — verified yes — "we strongly recommend that you implement these three in each and every app" — For us: the glow test cites WCAG; Meta names ISO 9241-391 (not read, paywalled).
- **Physical movement while seated/leaning must not push the camera into walls** — Meta, "Locomotion types", 2025-12-17, https://developers.meta.com/horizon/design/locomotion-types/ — verified yes — "will this move the virtual camera into solid geometry like walls" — For us: a standing player leaning into the corridor wall needs handling (fade or collision).

## 2. Movement settings — our pending decision (synthesis of the sources above and below)

- **Must/should offer** (Meta "Locomotion user preferences" 2026-09-08; VRC.Quest.Accessibility.7 and .8, both recommended): teleport and slide; snap and smooth turn; snap angle 30/45/90; smooth-turn speed; comfort assistance (vignette); direction mapping for slide; seated mode ("Locomotion comfort and usability"); either-hand use / remapping (see section 4). Movement speed is NOT named by Meta's design pages as a setting; IWSDK's own example offers it (3/5/8 m/s). — verified yes — "Allows users to choose between teleportation and slide" — For us: this is the full list of switches our settings page needs; speed is optional.
- **Defaults Meta names**: teleport + snap turn (user preferences page; IWSDK Locomotion Overview 2026-09-04 says the same). Meta's design pages give no default snap angle, vignette strength or turn speed. IWSDK code defaults: snap 45°, smooth turn 180°/s, vignette `comfortAssist` 0.5 on a 0–1 scale, slide 5 m/s (see section 13). — verified yes (pages and source code) — "Offer teleport and snap turn as comfort-oriented defaults" — For us: our defaults already match.
- **Where settings live**: Meta's answer is the in-app menu opened with the left Menu button (VRC.Quest.Input.1, recommended; "Controllers Best Practices" 2026-09-25 calls it strongly recommended); for hands, a palm-up index pinch of the non-dominant hand ("Hands UI best practices" 2026-09-24). When the menu button is not used, Meta's own samples show two fallbacks: Meta's Unity locomotion sample opens its preference menu with **B** (listed on the user-preferences page), and Meta's IWSDK locomotion example toggles its settings panel with the **left trigger** and places it 2.2 m ahead at head height − 0.25 m (min 0.8 m) (`examples/locomotion/src/panel.ts`). — verified yes — "Working preference menu example (B to open, A to select)" — For us: Menu if readable; otherwise one of Meta's two documented fallbacks (B, or the left trigger), or a fixed settings spot in the corridor.
- **Whether the web page can read the left Menu button**: conflicting Meta sources, must be probed on the owner's headset (browser 152). See section 4. — verified (sources read), behaviour unverified — For us: one probe run decides the binding.
- **Ask at first launch?** Meta never says to force a locomotion questionnaire. It says: comfortable defaults with opt-in to intense modes (user preferences); let people set up and save preferences early (Accessibility 2026-04-06); offer the seated/standing choice early, e.g. in tutorials ("Locomotion comfort and usability"); offer a left-handed toggle before handedness matters (Onboarding best practices 2026-09-15). — verified yes — "People need to be able to set their accessibility preferences early on" — For us: defaults on, one short early screen (posture + preset), the full menu always reachable.

## 3. User interface: panels, distances, text, targets, rays, feedback

- **Fixate-for-long content at ≥0.5 m; ~1 m comfortable for menus and GUIs** — Meta, "Display", 2026-03-11, https://developers.meta.com/horizon/design/display/ — verified yes — "Many have found that 1 meter is a comfortable distance for menus" — For us: clipboard at ~1 m agrees.
- **Place content roughly 1 m away, slightly below line of sight; avoid content appearing suddenly close or large** — Meta, "Key considerations", 2025-10-07, https://developers.meta.com/horizon/design/mr-design-guideline/ — verified yes — "roughly 1 meter distance slightly below the user's line of sight" — For us: clipboard height slightly under eye level.
- **Ray (indirect) UI comfortable 0.8–3 m; avoid 0.5–0.8 m middle zone; touch UI at 42–46 cm** — Meta, "Hands UI best practices", 2026-09-24, https://developers.meta.com/horizon/design/hands-ui-best-practices/ — verified yes — "Indirect interaction is comfortable from roughly 0.8m to 3m" — For us: clipboard for laser use belongs at ≥0.8 m, never 0.5–0.8 m.
- **Minimum hit target 48 dp = 22 mm = 3° at 0.42 m; visual target ≥32 dp; invisible hit slop** — Meta, "Accessibility", 2026-04-06, https://developers.meta.com/horizon/design/accessibility/ — verified yes — "22mm x 22mm / 48dp x 48dp / 3˚FOV at 0.42m" — For us: every clipboard button's collider ≥3° at its real distance (≈52 mm at 1 m, my arithmetic).
- **Angular collider 2.5–3° for touch and ray; 12 mm spacing between interactables; primary controls 60×60 dp for hand tracking** — "Hands UI best practices" and "Inputs and hit targets", 2026-04-19, https://developers.meta.com/horizon/design/styles_inputs_hit_targets/ — verified yes — "Minimum spacing: 12mm between adjacent interactables" — For us: answer buttons on one sheet must not touch.
- **Text: sans-serif, high x-height, no italics, regular weight for body; ≥14 px legible, ≥18 px comfortable (panel units); heavier weights more legible** — Meta, "Typography", 2026-04-19, https://developers.meta.com/horizon/design/styles_typography/ — verified yes — "Do not use italics, as they do not render well" — For us: no italics on the clipboard; px are panel units, not angles (see Gaps).
- **Contrast 4.5:1 normal text, 3:1 large text and UI parts; don't use colour alone** — Meta, "Color", 2026-04-19, https://developers.meta.com/horizon/design/styles_color/ — verified yes — "4.5:1 for regular-sized text and 3:1 for large text" — For us: agrees with our checklist.
- **Avoid pure white and black: light backgrounds no brighter than #DADADA, dark no darker than #1A1A1A** — same page — verified yes — "use colors no brighter than #DADADA" — the page applies it "to text, backgrounds, and all UI elements" — For us: paper, ink and controls keep inside both limits (src/engine/ui/sheet-math.js, docs/research/vr/08-paper.md).
- **LCD Quest panels cannot separate brightness below 13/255 (8-bit sRGB); author dark scenes brighter** — "Display" — verified yes — "below 13 out of 255 for 8-bit sRGB" — For us: dark corridor details below 13/255 will vanish on Quest 3.
- **No traditional HUDs; build information into the world; reticle drawn on the target** — "Display" — verified yes — "We discourage the use of traditional HUDs" — For us: nothing head-locked; the ray cursor sits on the clipboard surface.
- **Headlocked menus and UI should be avoided** — Meta, VRC.Quest.Functional.10 (recommended), https://developers.meta.com/horizon/resources/vrc-quest-functional-10/ — verified yes — "Headlocked menus and UI elements are generally uncomfortable" — For us: settings panel must be world-placed (or a slow leashed follower), not head-locked.
- **If the user is not facing the UI, give direction or let the UI follow** — Meta, "Content guidelines overview", 2026-07-07, https://developers.meta.com/horizon/resources/publish-content-consider/ — verified yes — "they should be given direction, or have the UI move with the user" — For us: when a sheet appears out of view, cue it (sound/arrow).
- **System ray specs: hit-test 10 m; visible beam 0.35 m (controllers), 0.25 m (hands); beam white on hover, #001E78 on select; cursor constant angular size, shrinks to ~83% on select; transitions hover 0.3 s, press 0.08 s, release 0.1 s, cursor fade 0.5 s** — Meta, "Ray casting specs", 2026-05-06, https://developers.meta.com/horizon/design/raycasting_specs/ — verified yes — "The visible laser extends 35 cm from the controller toward the target" — For us: copy the system laser so it feels native.
- **Ray affordances: hover = system hover haptic, no audio; select = press haptic + 3D click sound at the hit point** — same page — verified yes — "3D-positioned click sound at the hit point" — For us: our click sound should come from the button, not the controller.
- **Feedback on every targeting and selection event by visuals, audio and controller haptics; magnetism for 3D objects but not 2D UI; no hover on hidden objects; never head ray as primary pointer** — Meta, "Ray casting best practices", 2026-09-14, https://developers.meta.com/horizon/design/raycasting_bp/ — verified yes — "Use visuals, audio, and controller-haptic feedback to confirm every targeting and selection event" — For us: matches our checklist.
- **Buttons have default, hover, pressed and disabled states; one primary button per view; specific labels** — Meta, "Buttons: Specs" 2026-02-26 and "Buttons: Best practices" 2026-02-27, https://developers.meta.com/horizon/design/buttons_bp/ — verified yes — "Use one primary button per view" — For us: one main answer button per clipboard sheet.
- **Tooltips stay 0.5 s after hover-off, fade in/out** — Meta, "Tooltips: Specs", 2026-02-26, https://developers.meta.com/horizon/design/tooltips_specs/ — verified yes — "Display the tooltip for 0.5 seconds after the user hovers off" — For us: only if we add hints on hover.
- **No layout changes on hover (progressive disclosure); no 2D scroll bars; panels level and facing the user** — "Hands UI best practices" — verified yes — "Avoid progressive disclosure of additional actions on hover" — For us: clipboard buttons must not move when hovered.
- **System panel sizes: default 1024×640 dp, min 384×500 dp, max 1440×1000 dp** — Meta, "Layouts", 2026-04-19, https://developers.meta.com/horizon/design/styles_layouts/ and "Panels", 2026-03-02 — verified yes — "By default the viewport will be 1024x640dp" — For us: only relevant if we ever ship a 2D panel app; our clipboard is a 3D object.
- **Default Spatial SDK panel density 500 dp per metre** — Meta, "Panel resolution and display options", 2026-03-04, https://developers.meta.com/horizon/documentation/spatial-sdk/spatial-sdk-2dpanel-resolution/ — verified yes — "Default: 500 dp per meter" — For us: shows dp has no fixed physical size; use the angle rules (3°) instead.

## 4. Input: controllers, buttons a page can read, hands, reserved gestures

- **Standard controller mapping: trigger = select; grip = grab; thumbstick = navigation/locomotion; X/A = select/accept; Y/B = back/cancel; Menu (left) = in-app menu; Meta button (right) = system, not customisable** — Meta, "Controllers", 2026-09-25, https://developers.meta.com/horizon/design/controllers/ — verified yes — "It is an OS-level feature and is not customizable" — For us: Y/B as "back" on the clipboard; never bind the Meta button.
- **Use the Menu button for menus** — Meta, "Controllers Best Practices", 2026-09-25, https://developers.meta.com/horizon/design/controllers-best-practices/ — verified yes — "Use the Menu button (≡) for menus is strongly recommended" — For us: the settings page should open on Menu if the browser gives it to us.
- **In-app menus activated by the left Touch Menu button (recommended, not required)** — Meta, VRC.Quest.Input.1, https://developers.meta.com/horizon/resources/vrc-quest-input-1/ — verified yes — "In-app menus should be activated with the menu button" — For us: recommended only; a fallback is allowed.
- **Quest Browser and the left Menu button (old doc): left palm pinch equals the left Menu button and exits the WebXR session** — Meta, "WebXR Hands", undated, https://developers.meta.com/horizon/documentation/web/webxr-hands/ — verified yes (as written) — "takes the user out of the WebXR session" — For us: possibly outdated, see next item.
- **Quest Browser and the left Menu button (newer): Meta's browser engineer added `menu` (left gamepad buttons[7]) to the Quest controller profiles because the browser would stop exiting WebXR on it** — immersive-web/webxr-input-profiles PR #259 by cabanier, merged 2024-06-10, https://github.com/immersive-web/webxr-input-profiles/pull/259 ; profile file meta-quest-touch-plus.json — verified yes — "will no longer exit WebXR when the menu button is clicked" — For us: likely readable as left `buttons[7]`; must be confirmed with tools/xr-probe.html on browser 152 before we design around it.
- **IWSDK lists `menu` among its gamepad component ids** — Meta IWSDK, "Stateful Gamepad", 2026-07-22, https://developers.meta.com/horizon/documentation/iwsdk/concepts/xr-input/stateful-gamepad/ — verified yes — "'thumbrest', 'menu'" — For us: supports the newer reading above.
- **The Meta/system button still brings up trusted browser UI; session goes `visible-blurred`** — W3C Immersive Web WG minutes, 2024-03-25, https://www.w3.org/2024/03/25-immersive-web-minutes.html (cabanier) — verified yes — "visible:blurred just indicates you don't have controls any more" — For us: our pause on visible-blurred is right.
- **Thumbstick sign: −1 is forward/left, +1 backward/right** — W3C, Gamepad (WD 2025-07-10), https://www.w3.org/TR/gamepad/ — verified yes — "-1 SHOULD correspond to "forward" or "left"" — For us: "stick forward" means axes[3] < 0 on Quest.
- **xr-standard mapping: buttons[0] trigger, [1] squeeze, [2] touchpad, [3] thumbstick; axes[2],[3] thumbstick** — W3C, WebXR Gamepads Module L1 (WD 2025-07-07), https://www.w3.org/TR/webxr-gamepads-module-1/ — verified yes — "buttons[0]: Primary trigger" — For us: Quest profile adds [4] X/A, [5] Y/B, [6] thumbrest, [7] menu (left).
- **Either hand must work; plan for one controller; remap left/right** — "Controllers" and "Accessibility" — verified yes — "ensure that interactions can be performed with either hand" — For us: the laser must work from whichever controller the player uses.
- **Picking up objects uses the grip button, not the trigger** — Meta, VRC.Quest.Input.2 (recommended) — verified yes — "use the Touch controller's grip button rather than the trigger button" — For us: if a room has grabbable things (levers?), grab with grip.
- **Hands: palm-up pinch is reserved; dominant hand → system menu, non-dominant → app menu; system gesture must not trigger app actions** — Meta, "Input hierarchy", 2026-09-14, https://developers.meta.com/horizon/design/interactions-input-hierarchy/ ; VRC.Quest.Input.8 (required if hand tracking is supported) — verified yes — "the system gesture is reserved, and should not trigger any other actions" — For us: if we enable hands, ignore pinches during a palm-up pose.
- **Selection fallback when no hands/controllers: head ray after 20 s; HMD volume buttons as click** — "Ray casting specs" and "Input hierarchy" — verified yes — "The system waits 20 seconds after losing all external input" — For us: system behaviour, not ours; do not use head ray as our primary pointer.
- **If the app claims an input modality on the Store, all targeting, selection and locomotion must work with that modality alone from launch** — Meta, VRC.Quest.Tracking.2 (required) — verified yes — "without being forced to switch to a different input modality midway" — For us: do not declare "hands" until the whole game works with hands.
- **Teleport binding in Meta's design input map: thumbstick UP (either hand), click to cancel, sideways = turn, quick pull back = 80 cm back step; slide: left stick moves, right stick turns** — Meta, "Artificial locomotion input maps", 2026-02-18, https://developers.meta.com/horizon/design/locomotion-input-maps/ — verified yes — "Quickly snapping the thumbstick down moves the user one step, 80 cm, back" — For us: our bindings match this page exactly.

## 5. Audio, including spatial audio

- **Spatial by default; avoid head-locked stereo; author sounds mono; avoid pure sine tones; content above 1500 Hz localises best** — Meta, "Immersive sound", 2026-03-11, https://developers.meta.com/horizon/design/immersive_sound/ — verified yes — "most sounds should be authored as monophonic (single channel) sources" — For us: corridor sounds (relay thunk, breaker clack) should be mono, positioned.
- **Distance law: each doubling of distance −6 dB** — same page — verified yes — "it would be -6dB when it's 10 meters away" — For us: Web Audio PannerNode "inverse" model with rolloff 1 gives this.
- **Audio latency ~100 ms is where head-rotation lag becomes noticeable** — same page — verified yes — "aim for around 100ms as the threshold" — For us: keep audio start latency well under this.
- **Comfortable volume; loud or jarring sounds can cause discomfort or pain; give users audio control** — Meta, "Audio", 2025-10-07, https://developers.meta.com/horizon/design/audio/ — verified yes — "loud or jarring sounds can cause discomfort or even pain" — For us: the breaker clack and buzzer need level checks.
- **Spatial audio support is recommended, not required** — Meta, VRC.Quest.Audio.1, 2024-07-31 — verified yes — "Apps should support 3D audio spatialization, although it is not required" — For us: we already use positioned sound.
- **Spatial sound reduces disorientation after teleports/blinks** — "Locomotion comfort and usability" — verified yes — "users can better orient themselves in the environment" — For us: a soft positioned sound at landing can help.
- **Audio-only cues need visual or haptic twins; support system live captions via standard audio APIs** — "Accessibility" (Hearing controls) — verified yes — "Avoid relying solely on audio cues for important information" — For us: every buzzer/point sound also shows on screen.

## 6. Boundary, guardian, space setup and play modes

- **Store play modes: Sitting = fully playable seated in stationary furniture; Standing and Roomscale = usable in 6.5' × 6.5'; sitting test: no standing, no reaching the floor, no pivot >90°** — Meta, VRC.Quest.Tracking.1 (required), revisions to 2024-07-31, https://developers.meta.com/horizon/resources/vrc-quest-tracking-1/ — verified yes — "pivot greater than 90 degrees left or right" — For us: each seated room must keep everything within ±90°.
- **Standing (accessibility VRC): all interactions from a fixed position, within 7' × 5'; items on the floor need distance grab** — Meta, VRC.Quest.Accessibility.9 (recommended) — verified yes — "the app must be completely usable within a 7' x 5' play area" — For us: note Meta's two different standing sizes (see conflicts).
- **Roomscale needs at least 6.5 × 6.5 ft (2 × 2 m)** — Meta Quest Help, "Recommended space required to use Roomscale", undated, https://www.meta.com/help/quest/1190192431422476/ — verified yes — "at least 6.5 feet by 6.5 feet (2 meters by 2 meters)" — For us: agrees with our note.
- **Stationary mode boundary defaults to 1 × 1 m centred on the user, adjustable** — Meta Quest Help, "Set up your boundary", "updated 6 weeks ago", https://www.meta.com/help/quest/463504908043519/ — verified yes — "default boundary area of 3 feet by 3 feet (1 meter by 1 meter)" — For us: the 1 × 1 m number is right but lives on this page, not the one we cite.
- **Boundary recommended at all times for fully immersive apps; content must not spawn outside it; do not encourage leaving it** — Meta, "General information for immersive experiences", 2026-09-04, https://developers.meta.com/horizon/design/mr-health-general/ ; "Passthrough" 2025-07-25 — verified yes — "A boundary is recommended at all times for fully immersive experiences" — For us: never ask the player to walk past the boundary; place clipboards inside it.
- **Approaching/looming content provokes dodging; fast motion and reverse moves are risky** — "General information for immersive experiences" — verified yes — "Approaching or looming content can lead to reactive behavior such as dodging" — For us: agrees with our "nothing flies at the face" rule.
- **Users must be able to reset forward orientation in Local space (long-press Meta button)** — Meta, VRC.Quest.Functional.9 (required) — verified yes — "the user must be able to reset their forward orientation" — For us: our recenter on WebXR `reset` covers this; keep it.
- **Don't require interactions outside the play area unless locomotion or indirect interaction exists** — Meta, "Head Best Practices", 2026-03-13, https://developers.meta.com/horizon/design/head-best-practices/ — verified yes — "Require interactions outside the user's boundary configuration" (as a DON'T) — For us: teleport makes the corridor fine in any space.
- **About half of users play seated, half standing, and they switch** — "Key considerations", 2025-10-07 — verified yes — "Expect that approximately half of users will play sitting down" — For us: design every place for both postures.
- **In passthrough MR, do not teleport the user** — "Key considerations" — verified yes — "do not use teleport to move the user or other content" — For us: future MR rooms need no artificial locomotion.
- **When switching MR ↔ VR, give time to reorient before tasks; transitions with fades** — "Boundaryless and contextual-boundaryless safety best practices", 2026-09-04 — verified yes — "provide time for users to reorient and adapt" — For us: no timed task right after a VR/MR switch.
- **Persistent anchors: max 8 per site in Quest Browser; not persistent in private mode** — Meta, "Mixed Reality Support in Browser", undated (written for Quest 2/Pro, Connect 2022), https://developers.meta.com/horizon/documentation/web/webxr-mixed-reality/ — verified yes — "A site can currently only create 8 persistent anchors at a time" — For us: agrees with our note; page is old.

## 7. Health and safety

- **Minimum age 10; children supervised by an adult; example session: 30 minutes then a 15-minute break; about 1 in 4,000 people may react to flashes** — Meta, "Health and safety warnings: Meta Quest 3", undated, https://www.meta.com/legal/quest/health-and-safety-warnings/quest-3/ — verified partly (read via WebFetch; the page renders dynamically) — "maximum use period of 30 minutes plus a break of 15 minutes" — For us: rooms short enough to finish within a session; easy pause and resume.
- **Design so users can take breaks and resume** — "Overview of immersive VR apps best practices" — verified yes — "design content in a manner that makes it possible for users to take breaks" — For us: save progress per room.
- **Photosensitivity: follow ISO 9241-391:2016** — same page — verified yes (the reference); standard itself not read — "ISO 9241-391:2016 as a standard for image content" — For us: our WCAG-based glow test is a reasonable proxy; ISO text unread.
- **Advise users on bright light/sunlight at launch (tracking)** — "Controllers Best Practices", "Head Best Practices" — verified yes — "for example through a note at application launch" — For us: optional line on the first sheet.

## 8. Onboarding and first-time experience

## Contradictions inside Meta's own sources (so we don't quote the wrong one)
- **Teleport stick direction**: design input map = thumbstick up/forward; "Adapting from controllers" table (2026-09-09) = "Thumbstick down"; IWSDK default binding = right stick pulled back. We follow the input-map page.
- **Slide speed**: design 1.4 m/s vs IWSDK default 5 m/s ("4–6 m/s reasonable").
- **Smooth turn default**: IWSDK system 180°/s vs IWSDK example panel default 120°/s.
- **Standing play area**: VRC Tracking.1 6.5' × 6.5' vs VRC Accessibility.9 7' × 5'.
- **Frame rate**: "Common VRC failures" (2026-05-01) still says the app must run at 72 fps; VRC Performance.1 itself (since 2024-08-07) requires ≥60 fps rendering at ≥72 Hz. It also lists Input.6, which the main table marks RETIRED, and calls Security.1 a "must" while the table marks it recommended.
- **Left Menu button in WebXR**: WebXR Hands page (undated) says it exits the session; PR #259 (2024-06-10) says the browser would stop doing that and exposes `menu`.
- **Framebuffer scale**: perf workflow suggests 0.8–0.9; VRC Performance.4 recommends ≥85%.
- **Panel distance for hands + controllers**: "Key considerations" says ~70 cm; "Hands UI best practices" says avoid 0.5–0.8 m.
- **Walking speed rounding**: 3 mph is 1.34 m/s, Meta writes 1.4; 6 mph is 2.68 m/s, Meta writes 2.8 (my arithmetic).
- **Pure white**: Color page says never #FFFFFF; ray specs use #FFFFFF for beam and cursor.
- **Distance law wording**: Immersive sound says "a doubling of distance is a halving of intensity" but gives −6 dB, which is a halving of sound pressure (halving intensity is −3 dB). The −6 dB figure is the usable one.
- **VRC Accessibility.6** test steps are copied from Accessibility.5 (brightness/contrast), a documentation slip.

## Top 15 for our game (ranked)
1. Default teleport + snap turn; slide and smooth turn as opt-in; switch live in VR; remember the choice (user preferences; VRC Acc.7/.8).
2. A settings page reachable at any time in VR: left Menu button if the browser gives it (probe left `buttons[7]` on browser 152 first); otherwise a documented fallback (Meta's Unity sample uses B; Meta's IWSDK example uses the left trigger) or a fixed spot in the corridor.
3. Settings contents: move style, turn style, snap angle 30/45/90, smooth-turn speed, vignette (off/standard/high), seated/standing, hand; optionally the three presets Recommended/Comfortable/Advanced.
4. Slide at 1.4 m/s reached instantly, vignette while moving; the corridor's close textured walls raise optic flow, so keep teleport the default.
5. Seated support: early posture choice, system height, artificial turning, nothing beyond ±90°, nothing on the floor (VRC Tracking.1).
6. Performance floor for the Store: ≥60 fps at 72 Hz, ≥85% render scale, first head-tracked frame within 4 s or a loading indicator.
7. Focus and pause: stop timers/points and hide controllers and the laser when the system menu or headset-off happens (Functional.2, Input.4).
8. Reading distances: clipboard ~1 m, slightly below eye level, ≥0.8 m for laser use, never in 0.5–0.8 m; long reading never under 0.5 m.
9. Targets: collider ≥3° (≈52 mm at 1 m), 12 mm apart, one primary button per sheet, no layout shift on hover.
10. Text and colour: no italics, sans-serif, contrast 4.5:1 (3:1 large/UI), paper ≤ #DADADA, ink ≥ #1A1A1A, no detail below 13/255.
11. Feedback on hover and press: visual + positioned click sound at the hit point + controller haptic; copy the system laser (0.35 m beam, constant-size cursor).
12. Nothing head-locked (VRC Functional.10); settings panel world-placed or a slow leashed follower.
13. Accessibility VRCs: meaningful sounds also visible; one-controller play; colour never alone; brightness/contrast and text-size options; captions within 32 × 2.
14. Health: breaks easy (Meta's example 30 + 15 min), photosensitivity standard ISO 9241-391, no looming content, boundary on, age 10+ platform.
15. Store path (optional): immersive PWA via Bubblewrap that enters VR on load (A-Frame `enterVR` on `renderstart`), consent inside VR, privacy policy with deletion, age group (13+ simplest), IARC, comfort rating, play modes honestly declared, no diagnostic claims from room results.

## Gaps (looked for, not found or not verifiable)
- **Left Menu button in Quest Browser 152**: sources conflict (old Meta page: exits session; 2024 PR: exposed as `menu`). Only a headset probe settles it (tools/xr-probe.html, log left `gamepad.buttons[7]`).
- **Vignette strength in numbers**: Meta design pages give none; only IWSDK's 0–1 `comfortAssist` (0.5 default, "0.4–0.6 common") with no angular field-of-view value.
- **Default snap angle and default smooth-turn speed**: Meta design pages name the options, not the default; only IWSDK code (45°, 180°/s).
- **Movement speed as a user setting**: not in Meta design pages; only in the IWSDK example (3/5/8 m/s).
- **Comfort-rating rubric**: only the three short definitions in App policies 5.1; nothing on how an optional smooth mode affects the rating or whether Meta reviewers override it.
- **Text size as a viewing angle**: Meta gives 14/18 px and dp for panels; dp has no fixed physical size (500 dp/m Spatial SDK default vs 48 dp = 22 mm at 0.42 m in Accessibility). No angular minimum for world-space text found.
